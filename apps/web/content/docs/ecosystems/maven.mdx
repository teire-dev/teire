## What Teire reads

Maven versions come from literal `<version>` tags, properties (5 levels deep) and local parents.

Gradle declarations are read from:

- `"group:artifact:version"` strings,
- `libs.x.y` catalog accessors,
- configurations from `implementation` and `api` to `kapt` and `ksp`,
- versioned plugins (`id 'org.springframework.boot' version '2.6.3'` and catalog `alias(libs.plugins.x)`), as the plugin's marker coordinate.

Versions come from `gradle.lockfile` when you have one, which also gives the transitive dependencies. Without it, a declared version is treated as a floor. The `mvnw` and `gradlew` wrappers are used when present. A version stays in its flavour: a `-jre` artifact never moves to `-android`.

## How breaks are found

japicmp compares the old and new jars' bytecode in two passes, leaving out `internal`, `impl` and `shaded` packages. Kotlin multiplatform libraries are read through their `-jvm` variant. Kotlin's `@Deprecated(level = ERROR or HIDDEN)` counts as removed, with its `replaceWith`.

Your sources are first matched through their imports: explicit, wildcard, static and Kotlin `as`. For a new major, the scan then compiles your project in the JVM sandbox (the dependencies fetched with the network, the compile offline) and reads the references out of your **compiled classes**, exactly as javac and kotlinc resolved them. Those type-level sites replace the textual ones, so an unused removed API reads **not affected**. A source file that uses the library but didn't compile (another source set, an Android variant) is unresolved and keeps the verdict **inconclusive**. Inlined constants and Kotlin `inline` bodies can't be seen in bytecode, so their textual sites stay. The fix reads the classes again after its own compile.

## How it upgrades

Teire changes only the version text, wherever it lives:

- Maven: the `<version>` tag, the property, or local `dependencyManagement`.
- Gradle: the coordinate string, the catalog `[versions]` entry (all entries sharing that `version.ref` move together), a `gradle.properties` variable, or a plugin's `version` in the plugins block or the catalog.
- Java: when the target's published metadata needs a newer Java than the build declares, the same change raises it.

Projects with a `gradle.lockfile` then run `dependencies --update-locks` for that module.

## How it verifies

Teire runs your real build once online so the dependencies download. Only a resolution failure counts at this stage. It does this on the unchanged repository first. Then, offline:

| Build | typecheck | test |
|---|---|---|
| Maven | `mvn -o test-compile` | `mvn -o verify` |
| Gradle | `gradle --offline testClasses` | `gradle --offline --continue test` |

The JDK follows your CI's `setup-java`, `.java-version`, `.sdkmanrc`, `.tool-versions`, or the Gradle toolchain or Maven release, else 21. Test tasks always run, never "up to date". Test counts come from Surefire or Teire's Gradle init script.

<Callout type="warn" title="Limits">
  Android projects aren't supported: there is no Android SDK or Android Gradle Plugin in the sandbox. Maven has no lockfile, so transitive dependencies and versions managed by a remote parent or BOM aren't read. Versions computed with `$` interpolation in Gradle scripts are unresolved.
</Callout>
