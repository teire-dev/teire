## How breaks are found

Teire downloads both `.gem` files, checks their sha256 and extracts the public methods, constants and `require` paths with Prism. Prism sees classes, modules and constants, methods from `def`, `attr_*`, `alias`, `define_method(:name)` and delegators, their visibility and their parameters. Teire also notes runtime dependencies the new version drops.

Your code is searched for:

- the gem's constants, as written,
- `require` of removed paths or dropped dependencies,
- method calls by name, only in files that reference the gem's top constant.

Keyword arguments are recorded per call.

The next version skips releases whose `required_ruby_version` rejects your Ruby. That Ruby is read from the lockfile, else assumed to be 4.0.9.

## How it upgrades

Prism finds the `gem "x", "…"` line (or `add_dependency` in a gemspec). Teire replaces only the requirement, and only if it excludes the target. Then the sandbox runs `bundle lock --update GEM --conservative`, with a cooldown so Bundler lands on exactly the analysed version.

The PR's supply-chain section names a native extension the target adds (from the gemspec in the `.gem`) and owners added or removed since the scan that first saw the installed version.

## How it verifies

The sandbox installs the Ruby your Gemfile or lockfile names, then runs `bundle install`. It starts PostgreSQL, MySQL or Redis when your CI's `services:` or `config/database.yml` needs them, and runs your database setup.

The checks:

- **tests**: your CI's test step, else RSpec, `bin/rails test` or `rake`,
- **typecheck**: `bin/rails zeitwerk:check` for Rails, `srb tc` for Sorbet, `steep check` for Steep.

The checks run with `RAILS_ENV=test` and only your CI's plain environment variables, never secrets.
